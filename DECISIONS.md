# DECISIONS

## Accepted
- AI claim scope (TR s1,s3): we will claim AI in all three areas: (1) question selection, (2) question difficulty classification, (3) proctoring, including detection of blocked/covered camera, another person present or assisting, devices/objects, off-screen assistance. Only claim what is actually shipped and tested; label each in docs. AI proctoring may need prior AB/NCVET approval (FR s2.3.6.2), so keep a human-review queue and never auto-penalise a candidate without review.
- Learner data repository (TR s25): built and run in-house. Keep an export interface (versioned JSON/CSV export + pull API with scoped credentials) so an NCVET-proposed agency can be fed later. Revisit only if NCVET instructs otherwise.
- Multiple sectors: the 5% question-bank rule is checked per sector applied for. Sector list is configuration, not code.
- **A-01 schema defaults (2026-10-09, review pass 3):**
  - Single-AA tenancy; `assessment_completed`; `EVIDENCE_REQUIRED_FOR_RESULT=false`.
  - `rejected` / `cancelled` terminal for this AA; cancel releases `assessorDayLocks`.
  - Soft SLA for `aa_admin`: late accept/assign/submit allowed with required `lateReason`; record `sla.breached` + audit; return `SLA_*` only when reason missing. `sla.breached` also computed on read + nightly job.
  - Holiday changes audit-logged; **no retroactive** recompute of stored dueAts.
  - Assessment window `assessmentStartDate`/`EndDate` (IST); clash = range overlap + different centre via transactional locks; **reassign** supported.
  - Assessor login → `emailQueue` → `awardingBodies.notificationEmails` (includes `capturedAt`; never fails login API).
  - Working-day counting SCHEMA §2.1; example anchor **Tuesday** 06 Oct 2026; 7 WD before 2026-11-20 → due end **2026-11-11 IST**.
  - Qualifications: `passMarkUnit` percent|absolute; `passMarks`; NOS `maxMarks` nullable; Absent from attendance; PUT results only `assessment_completed`+`draft`; `RESULT_INCOMPLETE` on submit.
  - `learners` stable; `candidates.learnerId`; candidate users `linkedProfileId` → learner.
  - loginEvents: validate by `capturedAt` window; accept status ≥ `assessor_assigned`; `lateSync` + skew flags.
  - Reassessment new batch; inherit fields; 1-year window from **first** assessment; initiator open Q22.
  - Auth refresh device-bound; `mustChangePassword` on admin-set passwords; login rate-limit constants.
  - Audit read scoped for ab_reviewer; ncvet_viewer read-all monitoring.
  - `RATE_LIMITED` / `DUPLICATE_RESOURCE`; redact `passwordHash`.

## Proposed
- Stack: Node/Express + MongoDB (replica set) + React/Vite + React Native/Expo. Reason: matches existing team skills and tooling.
- Multi-tenant from day one? (one AA per tenant vs. single AA). Needs human decision. Phase 1 schema assumes single AA.
- **B-01 `auditLogs` document (2026-10-10):** SCHEMA §3.15 says "as before" and does not list fields. Implemented append-only rows: `actorId`, `actorRole`, `action`, `entity`, `entityId`, `abId`, `batchId`, `before`, `after`, `meta`, `ip`, `createdAt`. `password`, `passwordHash`, `passwordResetToken`, `passwordResetTokenHash`, `refreshToken`, and `tokenHash` are stored as `"***"`. Query indexes not yet in SCHEMA: `{ entity: 1, entityId: 1, createdAt: -1 }`, `{ abId: 1, createdAt: -1 }`, `{ createdAt: -1 }`. Architect: please fold this into SCHEMA.md.
- **B-01 response shapes:** `GET /audit-logs` returns `{ page, pageSize, total, items }` with `pageSize` 20 (contract lists `page` only). `POST /auth/refresh` returns the same session body as login (new access and refresh tokens plus `expiresInMs`, `offlineSessionMaxMs`, and `user`).
- Refresh tokens are opaque random values stored as SHA-256 hashes, not JWTs.
- **B-02 working-day admin (2026-10-10):** SCHEMA §3.15 says workingDayConfig and holidays are "as before" and lists no fields. API_CONTRACT.md has no response bodies. Until open questions 25–30 are confirmed, B-02 uses:
  - `workingDayConfig` singleton `{ key: "default", weekendDays: number[], updatedBy }`. `GET /api/v1/admin/working-day-config` returns `{ weekendDays, timezone }` and includes `id` after the first `PUT`. `timezone` echoes `TIMEZONE` and is not writable. `PUT` body is `{ weekendDays }` (unique integers `0..6`, at most 6, so one weekday remains). The first `GET` does not insert a row.
  - `holidays` `{ date: YYYY-MM-DD, name, region: string|null, createdBy }` with unique `{ date, region }`. `region: null` is AA-wide. `POST` returns `201` `{ id, date, name, region }`. `GET` returns `{ items }` with optional `from`, `to`, and `region`. `DELETE /api/v1/admin/holidays/:id` returns `204`.
  - A-03 supersedes this pair. `ASSIGN_SLA_MODE` and `RESULT_SLA_ANCHOR` are not the contract. B-02 on `main` still implements them; that branch must change as in the A-03 accepted decision.
  - Due helpers load AA-wide holidays unless the caller passes a region. A regional holiday applies only for that region. Batches have no region field yet.
  - Holiday and weekend writes do not update `batches`.
- **F-01 web shell (2026-10-10):** React 18, Vite, TypeScript, React Router 6, and TanStack Query. No third-party component library; pages use semantic HTML and CSS in `web/`. Access and refresh tokens stay in memory for the page session. `device.platform` sent to auth is `web`. SME has a landing page because `UserRole` includes `sme`. The candidate route is only a placeholder landing; question 23 still defers a candidate portal.
- **M-01 offline queue (2026-10-10):** AsyncStorage holds the login-event queue (the task allows AsyncStorage or SQLite). The role note prefers SQLite; switch when M-02 adds the batch/roster cache if we want one store. Tokens stay in expo-secure-store. `EXPO_PUBLIC_LOGIN_EVENTS_MODE=live` calls the contract paths; any other value uses an in-memory mock (default). The mock sets `lateSync` when the IST calendar date of receive time is after the IST date of `capturedAt`. It does not apply the SCHEMA "after the assessment window" clause (no batch window on device yet). For assessor `login` only, the mock sets `abEmailQueuedAt` to the receive time and leaves `abEmailSentAt` null; it does not write `emailQueue`. Offline use is allowed while `now - lastOnlineAuthAt < offlineSessionMaxMs` from the last successful online login or refresh (server value, else SCHEMA `OFFLINE_SESSION_MAX_MS`). At the limit the app deletes the local session and requires password login, including if the network just returned. A retryable sync error blocks later events; `409 CONFLICT_IDEMPOTENT` is kept and shown, and later events for that user still sync. Events for a different `userId` stay queued and are not sent with someone else's token.
- **B-08 users and email queue (2026-10-11):** The contract lists user paths and the two password-reset bodies. SCHEMA §3.12 names `pending|sending|sent|failed`, `attempts`, and `nextAttemptAt`, and does not list the other queue fields or the retry numbers. Until open questions 37–43 are confirmed:
  - Public user: `{ id, email, name, role, active, mustChangePassword, linkedProfileId, abId, tpId, createdAt, updatedAt }`. Missing profile ids are `null`. Responses omit `passwordHash`, reset-token fields, and tokens.
  - `GET /api/v1/users` accepts `role`, `active` (`true`|`false`), `page` (default 1), and `pageSize` (default 20, max 100). Response `{ page, pageSize, total, items }`.
  - `POST` returns `201` in that shape. An admin-set `password` sets `mustChangePassword: true`. Optional create fields: `linkedProfileId`, `abId`, `tpId`, `active` (default true). `PATCH` accepts `email`, `name`, `role`, `active`, `linkedProfileId`, `abId`, and `tpId` (`null` clears an id). `PATCH` rejects `password` and `mustChangePassword`.

Both modes set `mustChangePassword: true`, revoke every active refresh token for that user, and write an audit row. Passwords are 8–200 characters.

The API response and the audit row do not include it. If the queue insert fails, the route still returns `202` with `emailQueued: false` after the password change.   - SMTP env: `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, all listed in `server/.env.example`. The worker starts only when host and from are set. Tests pass a fake transport. The API does not send mail during the request. Error logs keep an uppercase code such as `EAUTH` and drop the error message.

  - Audit: `auth.password_changed`, `auth.password_change_failed`, `auth.password_change_rate_limited`. The request body is stored with `currentPassword`, `newPassword`, and `refreshToken` as `"***"`.
  - Dependencies: `nodemailer` 6.10.1 → 10.1.0 (needs Node 20 or later, which `server/package.json` already requires). The transport calls (`createTransport`, `sendMail` with a `to` array) are unchanged. `npm audit --omit=dev -w server` still lists one high item, `postcss` 8.4.49. 260. **Which fields are encrypted.** Built: `users.email`, `assessors.email`, `proctors.email`, `learners.phone`. The brief names candidate email, date of birth and address as well, but the schema has none of them (SCHEMA PII rule: no personal fields beyond the list), so nothing was added; the plugin takes any new field with one line. 263. **No deletion yet, and what deletion will mean.** The job only counts. 264. **Key management is environment variables.** Keys sit in the server's environment, which suits one host. Open: use a secret manager or KMS (the app would need a small change to fetch keys at start), who holds the master copies, and where the keys are backed up (never next to the database backup, but losing them makes the data unreadable for good). Rotation is manual: add the new key, change `FIELD_ENCRYPTION_KEY_ID`, restart, run `npm run migrate:encrypt`, remove the old key only after that run reports nothing rotated. Rotating `FIELD_HASH_KEY` needs the same run and a short window where email lookups fail. Is manual rotation acceptable, and how often?
265. **No partial search on email or phone.** Equality only, through the hash. Regex, prefix, range, sort and `$inc` on an encrypted path are refused. The users list has no email search today, so no screen breaks. Confirm admin screens do not need "email contains" or sort by email.
266. **What counts as reading personal data.** Logged: lists and details of users, learners, assessors, proctors, and the batch roster (by learner). Not logged: results and result change logs, attendance and checklist reads, login events, batch reads (which name no people), exports (S-03 will log its own), and `POST /auth/login`, which returns the user's own record. Reads of your own record (an assessor reading themselves, a candidate their own learner row) are logged like any other. Should result, attendance and login-event reads be logged too (they name learners), and should self-reads be left out to cut noise?
267. **A read that cannot be logged is refused.** The response is `500` and no data is returned if the access-log write fails, matching how audited writes behave. The cost is that a database problem on the log collection stops these reads. Confirm, or serve the data and raise an alert instead.
268. **Who may read the access log.** `aa_admin` only. `mis`, `ncvet_viewer` and the data principal themselves (a learner asking "who looked at my data", a DPDP right of access) get nothing. Should `ncvet_viewer` or `mis` read it, and how is a learner's request answered (an admin runs the filter and sends it)?
269. **Development keys outside production.** With no keys set, a development or test run uses a built-in key and prints a warning once; only `NODE_ENV=production` refuses to start without keys. Any staging site that runs with `NODE_ENV=development` and real data would be encrypted with a key that is in the source. Confirm staging runs as production, or make the keys mandatory everywhere except `NODE_ENV=test`.
270. **Migration needs a short maintenance window.** Login looks the user up by `emailHash`, so until `npm run migrate:encrypt` has filled the hashes, nobody can sign in. Order: set the keys, deploy, run the migration, done. A lookup that falls back to the plain email during the window was not built. Accept the window, or add the fallback for one release?
271. **Disk and transport encryption are not this task.** Field encryption protects against someone reading the database or a backup. It does not replace encryption of the database volume, TLS to MongoDB, TLS to the API, or encrypted backups, and the repository does not configure any of them. Who owns those, and where is it written down (TR s18 B asks for documented procedures)?
272. **DPDP roles and age.** The checklist (docs/DPDP_CHECKLIST.md) needs someone named as Data Fiduciary contact, a grievance officer, and a decision on the lawful basis (consent or a legitimate use) for learner data collected through training partners. V-01 open questions (2026-10-15, Evidence vault backend). V-01 uses 320 upward.
320. **No delete, no overwrite, no edit.** The storage interface has no delete and the local driver refuses an existing key; the model rejects edits and deletes of evidence rows except the verification fields. Evidence of cancelled and rejected batches is kept. This conflicts with DPDP erasure and with storage cost over time. Who may erase evidence, after which period, and by what process outside the API (DPDP-3, retention periods Q262)? Give the application's storage credentials no delete permission so this holds even if there is a bug.
321. **Orphaned objects.** The file is stored before the row is written. If two uploads with the same `clientEventId` arrive together, or the database write fails, a stored object has no row, and nothing can delete it. They are harmless but cost space and are unreferenced personal data. A reconciliation report (objects with no row) is not built.
322. **Hosting provider and region.** Following the 2026-10-15 human decision, files go to S3-compatible storage in India; the provider is not chosen. The code only needs bucket, region, endpoint and credentials. Confirm the provider, the in-India region, and that the provider's own backups and replicas also stay in India. Q6 and Q240 stay open until then.
323. **Encryption of files at rest.** The application does not encrypt file bytes (S-01 field encryption covers a few database fields only). It relies on provider-side encryption and, for local disk, on the host. Confirm that bucket encryption is on, who holds the keys, and whether an application-level layer is wanted (it would block provider-side previews and is more work).
324. **No virus or content scan.** The type is checked from the first bytes only. A file can start like a valid JPEG and still carry other content. Files are served as `attachment` with `nosniff` and only four media types are accepted, but no scanner runs. Decide whether to add one (ClamAV or a provider service) before V-02 shows files in a browser, and whether images are re-encoded to strip metadata and hidden payloads.
325. **What is access-logged.** Every file download is logged (the evidence row, plus the learner when a candidate is named). List and detail reads of the metadata are not, although they carry uploader, location and time. Confirm.
326. **Who sees which rows.** Assessor and proctor see only what they uploaded, not what the other uploaded on the same batch; after a reassignment the new assessor sees none of the old evidence. `tp` and `candidate` never see evidence, including a candidate's own photo. `mis` and `ncvet_viewer` see all rows and download all files. Confirm, and whether a reviewer from the awarding body may download ID proofs.
327. **Location is optional.** Location may be absent (`not_provided`), because Guidelines 4.11b asks for geo-tags on offline and blended batches and the batch mode is not checked. Should an offline or blended batch require a fix, or an `unavailable` reason, on `photo` and `video` evidence? No coordinates are compared with the centre's location.
328. **No capture window check.** Login events must fall inside the assessment window; evidence `capturedAt` is accepted as sent (early or late files, a device clock set wrong). Add the window check, a clock-skew flag like the login event's, or leave it to the reviewer?
329. **Download response differs by driver.** With S3 the endpoint returns JSON with a short-lived link; with local disk it returns the bytes. The V-02 browser and the mobile app must handle both. The link is a bearer link: anyone who holds it can read the file until it expires, and the provider's logs see that download, not our access log. A proxy that always streams through the API would give one path and one log, at the cost of server bandwidth. Decide before V-02.
330. **Limits and format list.** Images and PDFs 25 MB, video 200 MB, formats JPEG, PNG, PDF and MP4 only. Phones often produce HEIC photos and QuickTime `.mov` video, and some video is above 200 MB; those are refused. Upload is not resumable, so a failed 200 MB upload restarts. The suite's 200 MB test sends a real 200 MB body.
331. **`kind` and type pairing.** `photo` accepts JPEG and PNG only, `video` accepts MP4 only, the other kinds accept JPEG, PNG and PDF. A video of kind `attendance` is refused. Confirm.
332. **Duplicate files.** The same bytes uploaded under two `clientEventId`s are stored twice. `sha256` is indexed so duplicates can be reported; nothing blocks them.
